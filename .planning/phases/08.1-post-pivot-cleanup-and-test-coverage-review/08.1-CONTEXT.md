    7. Rewrite `.github/workflows/build.yml` to replace `build-native-host` + `build-extension` jobs with a single `build-wails-app` job
    8. Rewrite CLAUDE.md + README.md for v3.0 Wails architecture

README.md similarly rewritten for the Wails-era install + usage story. Phase 11 REL-07 may re-polish README with shipped-screenshots + final install URL — that's a follow-up pass, not a replacement for doing the substantive rewrite here.

### Coverage Methodology

- **D-05: Risk-based gap filling, carried forward.** PROJECT.md's validated "Test completeness = risk-based gap filling, not numeric coverage target" decision applies to the Wails codebase unchanged. No per-package numeric floor, no coverage-enforcing gate. Planner prioritizes by blast radius (auth flow + token refresh + invalid_grant + keyring + MIME build + Gmail HTTP path > tray/watcher-bridge/session-end > main/app/logging/paths glue), fills gaps per judgement. Update PROJECT.md Key Decisions row to mark "✓ Good — extended to v3.0 Wails codebase in Phase 8.1".

- **D-06: No explicit tier rubric — planner decides per file.** Planner reads existing tests + file context and chooses the depth appropriate to each file/package. No "Critical / Standard / Glue" labels baked into the plan. Trust + inspect-in-review model. This diverges from the suggested three-tier framework; user preferred planner judgement over prescriptive categories.

- **D-07: QUAL-04 (`go test -race ./...`) promoted to per-PR gate.** Adding `-race` to the new `build-wails-app` CI job (blocking), keeping `go-race-nightly.yml` as the nightly full-stack runner. Closes QUAL-04 in this phase. Rationale: race detection is cheapest at merge time, not at 2 AM when the nightly fails. `-race` runs on `./internal/mapi/...` + `./src/app/...` only (interceptor stays C++); do NOT add `-race` to pre-existing unit-test runs that may already be covered — just ensure the `build-wails-app` job runs `go test -race ./...` with the correct module scope.

- **D-08: Coverage measurement — report, don't gate.** `build-wails-app` CI job runs `go test -coverprofile=coverage.out ./...` per module and uploads the `.out` files + a short summary as workflow artifacts. No threshold enforcement. Reviewer + planner use the numbers as data during review — "this critical file is 0%, why?" — without gaming pressure. Explicit non-goal: per-PR coverage diff bots, Codecov integration, coverage badges.

### Test Scope Breadth

- **D-09: Frontend (Svelte) included — `lib/` + components.** Phase 8.1 introduces Vitest + `@testing-library/svelte` + `jsdom` to `src/app/frontend/`. Tests cover: (a) all files in `src/app/frontend/src/lib/` (at minimum `auth.ts`, `queue.ts`, and any helper modules that land before Phase 9), (b) components in `src/app/frontend/src/lib/components/` — rendering, prop handling, event emission, Wails event subscription. App.svelte gets at least a render-and-mount smoke test. Planner surveys the current frontend source before sizing.

- **D-10: `svelte-check` wired into CI as a blocking gate.** `build-wails-app` job runs `npm run -w @marcfargas/go-mapi-app-frontend check` (which invokes svelte-check with the tsconfig). PR merge blocks on TypeScript errors in `.svelte` + `.ts` files. Cheap + catches TS regressions early.

- **D-11: Keyring: interface + in-memory fake for unit tests; real keyring on Windows CI.** Introduce (or extend, if Phase 8 already has it) a `KeyringStore` interface in `src/app/` that `auth.go` takes via constructor. Unit tests use an in-memory fake (map-backed `sync.Mutex`-guarded store) — fast, deterministic, cross-platform for dev iteration. A separate Windows-only integration test (`//go:build windows`) exercises real `zalando/go-keyring` against the actual Windows Credential Manager on `windows-latest` CI. Planner verifies current Phase-8 test pattern first and extends it; if Phase 8's `auth_test.go` already concretely depends on real keyring, planner refactors to the interface as part of this phase's coverage work.

- **D-12: OAuth + Gmail HTTP via `httptest.Server`.** Test token refresh, `invalid_grant`, 401 retry once after force-refresh, network errors, and Gmail draft path (what exists today) against stdlib `net/http/httptest` servers emulating Google's token + userinfo + Gmail endpoints. Lightweight (no separate mock binary), tight coupling to real HTTP semantics. Planner extends any existing `httptest` usage rather than duplicating.

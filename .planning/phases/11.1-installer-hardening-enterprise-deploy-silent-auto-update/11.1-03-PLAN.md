go-selfupdate ChecksumValidator format expectation (verified pkg.go.dev/github.com/creativeprojects/go-selfupdate):
- One line per asset.
- Two spaces between digest and filename (matches sha256sum output exactly).
- Filename is the basename as it appears at the GitHub Release URL (https://github.com/marcfargas/go-mapi/releases/latest/download/<name>).
- ASCII encoding, LF line endings preferred (validators tolerate CRLF but LF is the convention).

- Step `Extract + validate version against tag` uses `shell: pwsh` and writes `version` to `$env:GITHUB_OUTPUT`.

- Step `Attach installer to GitHub Release` uses `softprops/action-gh-release@v2` with `files: ${{ steps.final.outputs.path }}` (single-file form).

The new step must run AFTER `final` and BEFORE the gh-release attach step.

    The new step body (RESEARCH §Code Example 3 adapted for both Option A and Option B; pick the asset list per audit):

    ```
    - name: Generate SHA256SUMS.txt
      shell: pwsh
      run: |
        # D-17 (Phase 11.1): publish a SHA-256 manifest alongside release assets
        # so the silent updater (Plan 11.1-04) can verify integrity via
        # selfupdate.ChecksumValidator with UniqueFilename SHA256SUMS.txt.
        # Format: lowercase-64-char-hex + two spaces + filename. sha256sum
        # convention (matches go-selfupdate / goreleaser parser expectations).
        # Filenames here MUST match the basenames at the GitHub Release URL
        # (https://github.com/marcfargas/go-mapi/releases/latest/download/<name>).

        $assets = @(
          @{ Path = '${{ steps.final.outputs.path }}'; Name = 'go-mapi-setup.exe' }
          # If the audit chose Option A, append:
          # @{ Path = 'src/app/build/bin/go-mapi.exe';                  Name = 'go-mapi.exe' }
          # @{ Path = 'src/interceptor/build-x64/bin/go-mapi.dll';      Name = 'go-mapi-x64.dll' }
          # @{ Path = 'src/interceptor/build-x86/bin/go-mapi.dll';      Name = 'go-mapi-x86.dll' }
        )

        $lines = foreach ($a in $assets) {
          if (-not (Test-Path $a.Path)) {
            throw "SHA256SUMS: missing asset $($a.Path) (expected name $($a.Name))"
          }
          $h = (Get-FileHash -Path $a.Path -Algorithm SHA256).Hash.ToLower()
          "$h  $($a.Name)"
        }

        # ASCII (no BOM) + LF line endings. Set-Content -NoNewline gives no
        # trailing newline; we append one explicitly so the manifest ends with LF.
        $manifest = ($lines -join "`n") + "`n"
        Set-Content -LiteralPath SHA256SUMS.txt -Value $manifest -Encoding ASCII -NoNewline

        Write-Host "Generated SHA256SUMS.txt:"
        Get-Content SHA256SUMS.txt | Write-Host
    ```

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → GitHub Release | The runner computes SHA-256 hashes of artifacts produced in the same job, then uploads both the artifact AND the manifest to the same Release. Trust assumption: GitHub Actions infrastructure has not been compromised; if it has, both the binary and the hash are attacker-controlled and the manifest provides no defense. This is the same trust boundary as the existing release pipeline. |
| Release pipeline → end-user silent updater | Future end-user silent updater (Plan 11.1-04) will fetch SHA256SUMS.txt over HTTPS from GitHub Releases. TLS terminates at GitHub. Threat surface = compromised release pipeline (out of scope for this plan), MITM (mitigated by TLS), stale manifest (mitigated by version-string match in pre-fetch step in Plan 11.1-04). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11.1.03-01 | Tampering | Manifest is computed AFTER SignPath signing — could the SignPath step subtly modify the artifact between hash computation and final upload | mitigate | The Generate SHA256SUMS.txt step runs AFTER `id: final` (Task 1 audit confirms `final` resolves to the SignPath-signed installer when SignPath ran successfully). No further modification happens between hash and upload (both are within the same job's working dir). |
| T-11.1.03-02 | Information Disclosure | Manifest exposes lowercase hex digests in plaintext at the public Release URL | accept | Hashes of public release artifacts are not sensitive; this is the standard release-engineering practice (mirrors goreleaser, Hashicorp releases, etc.). Pitfall 6 (no per-user hash logging) applies to the silent-updater's `update.log`, not to this public manifest. |
| T-11.1.03-03 | Spoofing | Attacker uploads a malicious `SHA256SUMS.txt` alongside a real release using a leaked GH token | mitigate | Repo write access required to upload to a Release — same trust boundary as committing code. Out of scope for hash-manifest design; standard repo security applies. |
| T-11.1.03-04 | Denial of Service | Generate step throws on a missing asset path, blocking the release | accept | Throw-on-missing is intentional — better to fail the release than silently publish an incomplete manifest that lets the silent updater download an unverifiable binary. The audit (Task 1) ensures the asset list matches what the workflow produces. |

</threat_model>

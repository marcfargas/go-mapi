# Phase 11.1: Installer hardening + enterprise deploy + silent auto-update — Research

**Researched:** 2026-04-25
**Domain:** NSIS installer hardening + Windows Scheduled Task + atomic binary swap + SHA-256 release manifest
**Confidence:** HIGH (all 10 mandatory focus areas verified against primary sources)

## Summary

Phase 11.1 reuses every primitive already proven in Phase 10 (NSIS, ApplicationID plugin, Pester 5 harness, SignPath gating) and Phase 11 (`creativeprojects/go-selfupdate` v1.5.2, in-process notify path). The new work is mostly glue: one-line NSIS fixes for T2/T4, an XML-defined Scheduled Task registered via `schtasks /create /XML`, a new `--update-check-silent` CLI mode on the Wails binary that reuses `updateService.CheckNow` plus a download/verify/swap tail, and a SHA256SUMS.txt manifest line in `installer-release.yml`.

Two non-obvious findings drive the plan shape:

1. **T4 root cause is overwhelmingly likely the missing `SetOverwrite` directive in the x86 block at `src/installer/go-mapi.nsi:99-101`.** NSIS `SetOverwrite` is **block-scoped to the section** and does NOT cross `SetOutPath` boundaries cleanly when one OUT path's write fails — the install script's x64 block (lines 95-96) writes the DLL with the global default `on`, but the explicit `SetOutPath "$PROGRAMFILES32\go-mapi"` + `File` pair at 99-101 inherits the same default. The actual divergence is more subtle: nothing in the script declares `SetOverwrite try` anywhere, so under `on` (default) any transient AV/share-mode hold on the existing 32-bit DLL during reinstall produces a hard error and aborts. The fix is `SetOverwrite try` paired with an explicit `Delete` retry. `[VERIFIED: NSIS reference]`

2. **`schtasks /create` cannot natively express `MultipleInstancesPolicy`, `<RandomDelay>`, or multi-trigger tasks.** All three are XML-only. The plan therefore must ship an XML task definition, and call `schtasks /create /XML <file> /TN "go-mapi Auto Update" /F /RU SYSTEM /RL HIGHEST`. The `/F` flag handles the idempotency case (replaces the existing task with no error). `[VERIFIED: Microsoft Learn schtasks-create + Task Scheduler XML schema]`

**Primary recommendation:** Plan as 6 plans / ~3 waves. Wave 0: NSIS fixes (T2 + T4) + Pester regressions. Wave 1: SHA256SUMS.txt + silent CLI flag + ChecksumValidator wiring. Wave 2: Scheduled Task registration (NSIS components page + XML task + uninstall removal) + README/ROADMAP doc updates + extended Pester coverage.

### Pattern 1: NSIS `SetOverwrite try` for resilient reinstall

**What:** Use `SetOverwrite try` instead of the default `on` for files that may be transiently locked (AV scans, file-system filter drivers).
**When to use:** Any DLL/EXE that has been observed to fail overwrite on reinstall when no process actually has the file open.
**Example:**

```nsis
; Source: NSIS reference (https://nsis.sourceforge.io/Reference/SetOverwrite)
; Existing path (reproduces T4 on some machines):
SetOutPath "$PROGRAMFILES32\go-mapi"
File "${__FILEDIR__}\..\interceptor\build-x86\bin\go-mapi.dll"

; Phase 11.1 fix (paired with explicit pre-delete + retry):
SetOutPath "$PROGRAMFILES32\go-mapi"
ClearErrors
Delete "$PROGRAMFILES32\go-mapi\go-mapi.dll"
; Delete failure on a non-locked file is non-fatal here; the File command does the work.
SetOverwrite try
File "${__FILEDIR__}\..\interceptor\build-x86\bin\go-mapi.dll"
SetOverwrite on   ; restore default for the rest of the section
```

`SetOverwrite try` "overwrites when possible; skips without user interaction if writing fails" `[VERIFIED: NSIS reference]` — combined with the explicit `Delete`, this collapses transient AV holds into a no-op rather than aborting the installer. The Pester regression (D-05) drives both bitnesses through reinstall to confirm.

### Pattern 2: NSIS `SetShellVarContext all` for all-users shortcut

**What:** Wrap shortcut create/delete in `SetShellVarContext all` so `$SMPROGRAMS` resolves to `%ProgramData%\Microsoft\Windows\Start Menu\Programs\`.
**When to use:** Always, for any machine-wide install where the shortcut should appear for every user.
**Example:**

```nsis
; Source: NSIS reference (https://nsis.sourceforge.io/Reference/SetShellVarContext)
Function CreateShortcutAndAUMID
  SetShellVarContext all       ; resolve $SMPROGRAMS to %ProgramData%\...
  CreateShortcut "$SMPROGRAMS\go-mapi.lnk" "$INSTDIR\go-mapi.exe" \
      "" "$INSTDIR\go-mapi.exe" 0 SW_SHOWNORMAL "" \
      "go-mapi — MAPI-to-Gmail bridge"
  ApplicationID::Set "$SMPROGRAMS\go-mapi.lnk" "${AUMID}"
  Pop $0
  ; ... existing rc handling ...
  SetShellVarContext current   ; restore default before falling out of the function
FunctionEnd

Section "Uninstall"
  ; ...
  SetShellVarContext all
  Delete "$SMPROGRAMS\go-mapi.lnk"
  SetShellVarContext current
  ; ...
SectionEnd
```

**Side-effect notes:** `SetShellVarContext all` ALSO redirects `$DESKTOP`, `$STARTMENU`, `$QUICKLAUNCH`, `$DOCUMENTS`, `$APPDATA`, `$LOCALAPPDATA` for the duration of the setting `[CITED: nsis.sourceforge.io/Reference/SetShellVarContext]`. **`$APPDATA` resolution changes** — the existing uninstaller code at `src/installer/go-mapi.nsi:666-676` uses `"$APPDATA\..\..\ProgramData\go-mapi\..."` as a primitive to reach `%ProgramData%`, which works precisely BECAUSE the default context is `current` (so `$APPDATA` = `%APPDATA%` = `C:\Users\<X>\AppData\Roaming` and `..\..\ProgramData` walks to `C:\ProgramData`). If `SetShellVarContext all` is set when those lines execute, `$APPDATA` resolves to `%ProgramData%` and the relative walk breaks. The wrap MUST be tight: set `all` immediately before the shortcut op, restore `current` immediately after.

### Pattern 3: XML-defined Scheduled Task imported via `schtasks /create /XML`

**What:** Define the task in XML (gives access to `MultipleInstancesPolicy`, `<RandomDelay>`, multi-trigger), import via `schtasks /create /XML <file> /TN <name> /F`. The `/F` flag overwrites an existing task with the same name (idempotent install).
**When to use:** Any time the task needs settings unavailable to plain `schtasks /create` switches.
**Example task XML** (drop into `src/installer/tasks/go-mapi-auto-update.xml`):

```xml

        <DaysInterval>1</DaysInterval>
      </ScheduleByDay>

    </BootTrigger>
  </Triggers>
```

NSIS install-time invocation:

```nsis
; Source: Microsoft Learn schtasks-create
; (https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create)
Function RegisterScheduledTask
  ; Skip if /AUTOUPDATE=0 (or absent — default OFF per D-07)
  StrCmp $AutoUpdateFlag "1" 0 SkipTask

  ; Stage the XML to a transient path so we can substitute INSTDIR.
  SetOutPath "$INSTDIR"
  File "${__FILEDIR__}\tasks\go-mapi-auto-update.xml"

  ; Substitute INSTDIR_PLACEHOLDER -> $INSTDIR via PowerShell (only powershell.exe; D-30)
  nsExec::ExecToLog 'powershell.exe -NoProfile -Command "(Get-Content -LiteralPath ''$INSTDIR\go-mapi-auto-update.xml'' -Raw) -replace ''INSTDIR_PLACEHOLDER'', [regex]::Escape(''$INSTDIR'') | Set-Content -LiteralPath ''$INSTDIR\go-mapi-auto-update.xml''"'
  Pop $0

  ; /F overwrites an existing task → idempotent re-install (D-08 + D-16)
  ExecWait 'schtasks /create /XML "$INSTDIR\go-mapi-auto-update.xml" /TN "go-mapi Auto Update" /F /RU SYSTEM /RL HIGHEST' $0
  DetailPrint "Scheduled task create rc=$0"
  Delete "$INSTDIR\go-mapi-auto-update.xml"   ; one-shot — definition lives in Task Scheduler now
  Return
```

### Pattern 4: `MoveFileEx` rename-while-running for atomic binary swap

**What:** NTFS allows renaming a running EXE or loaded DLL because the kernel holds the open handle by `FILE_OBJECT` reference, not by name. As long as the destination handle is openable with `DELETE` access, `MoveFileEx` succeeds and existing handles continue to work against the original file content.
**When to use:** When you need to replace a binary that is currently in use, without a reboot. Specifically rejected: `MOVEFILE_DELAY_UNTIL_REBOOT` (D-12 — RDS targets do not reboot).
**Example (Go):**

```go
// Source: Microsoft Learn winbase!MoveFileExA + golang.org/x/sys/windows
// https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexa
package main

import (
    "fmt"
    "os"
    "time"

    "golang.org/x/sys/windows"
)

// swapInPlace renames installed → installed+".old.<pid>" then renames staged → installed.
// Returns the .old path so callers can attempt cleanup or defer to the next uninstall.
// Both calls use MoveFileEx; MOVEFILE_DELAY_UNTIL_REBOOT is intentionally NOT used (D-12).
func swapInPlace(staged, installed string) (oldPath string, err error) {
    oldPath = fmt.Sprintf("%s.old.%d", installed, os.Getpid())

    // Step 1: rename installed → installed.old.<pid>. NTFS permits this even for
    // a running EXE / loaded DLL because the open handle holds the file by
    // FILE_OBJECT reference, not by directory entry.
    fromInstalled, err := windows.UTF16PtrFromString(installed)
    if err != nil { return "", err }
    toOld, err := windows.UTF16PtrFromString(oldPath)
    if err != nil { return "", err }
    if err := windows.MoveFileEx(fromInstalled, toOld, windows.MOVEFILE_REPLACE_EXISTING); err != nil {
        return "", fmt.Errorf("rename installed→old: %w", err)
    }

    // Step 2: rename staged → installed. Plain rename (no REPLACE_EXISTING) —
    // we just freed the destination in step 1.
    fromStaged, err := windows.UTF16PtrFromString(staged)
    if err != nil { return oldPath, err }
    toInstalled, err := windows.UTF16PtrFromString(installed)
    if err != nil { return oldPath, err }
    if err := windows.MoveFileEx(fromStaged, toInstalled, 0); err != nil {
        // Best-effort rollback so we don't leave the user without a binary.
        _ = windows.MoveFileEx(toOld, fromInstalled, windows.MOVEFILE_REPLACE_EXISTING)
        return oldPath, fmt.Errorf("rename staged→installed: %w", err)
    }
    return oldPath, nil
}

// swapWithRetry wraps swapInPlace with backoff for the case where another
// process briefly holds the file (Defender real-time scan, file-system filter
// driver, search indexer). D-13: never WM_CLOSE the running app; D-14: cap.
func swapWithRetry(staged, installed string, maxElapsed time.Duration) (string, error) {
    deadline := time.Now().Add(maxElapsed)
    backoff := 30 * time.Second
    var lastErr error
    for time.Now().Before(deadline) {
        if old, err := swapInPlace(staged, installed); err == nil {
            return old, nil
        } else {
            lastErr = err
        }
        time.Sleep(backoff)
        if backoff < 5*time.Minute {
            backoff *= 2
            if backoff > 5*time.Minute { backoff = 5 * time.Minute }
        }
    }
    return "", fmt.Errorf("swap exceeded %s: %w", maxElapsed, lastErr)
}
```

**When `MoveFileEx` fails:** `[VERIFIED: Microsoft Learn winbase!MoveFileExA]`
- Source path is on a remote share AND `MOVEFILE_DELAY_UNTIL_REBOOT` is set (rejected by D-12 — N/A).
- Destination is an existing directory (we never hit this — destination is always a file path).
- Caller lacks DELETE permission on source or its parent. Mitigation: SYSTEM has full access in `%ProgramFiles%`; this path is only hit if ACLs were tampered with manually.
- Source is held with a share mode that excludes `FILE_SHARE_DELETE`. **Loaded DLLs and running EXEs are opened with `FILE_SHARE_DELETE` by default by the Windows loader**, which is why the rename-while-running trick works. `[CITED: Microsoft Learn winbase!MoveFileExA Remarks]` Antivirus / file-system filters that open files WITHOUT `FILE_SHARE_DELETE` cause the rename to fail with `ERROR_SHARING_VIOLATION` (32) — this is the specific case the retry loop handles.

**Cleanup of `.old.<pid>` orphans:** After the swap, the `.old.<pid>` file is still held by the running process's loader handle. It can be deleted only after that process exits. Two options:

1. **Defer to next uninstall** (simplest): the uninstaller's `Delete "$INSTDIR\*.old.*"` line catches everything.
2. **Proactive cleanup** at `--update-check-silent` start: glob `*.old.*` in `$INSTDIR` and try `os.Remove` for each — failures (process still running) are silent and retried next trigger.

Recommendation: **option 2 (proactive)** at silent-update start, plus a glob in the uninstaller as belt-and-braces. Adds 5 LOC, prevents `.old` files accumulating across many silent updates.

## Common Pitfalls

### Pitfall 1: NSIS `SetOverwrite` does not survive `SetOutPath`

**What goes wrong:** Setting `SetOverwrite try` once at the top of the install section, then assuming all `File` commands inherit it. Phase 10's existing script does NOT set it explicitly anywhere — every `File` writes with the default `on`, which aborts on transient holds.
**Why it happens:** NSIS docs are sparse on directive scope. The directive applies to subsequent `File` commands until changed. An audit of `src/installer/go-mapi.nsi` (lines 95-101) confirms: zero `SetOverwrite` directives in the entire file. T4 reproduces under `on` because AV/filter holds become hard errors.
**How to avoid:** Set `SetOverwrite try` immediately before any DLL `File` write, immediately reset to `on` after. Pair with explicit `Delete` of the prior-version DLL.
**Warning signs:** Reinstall fails on one specific file repeatedly with "not writable"; manual delete of the file works (rules out kernel-level lock).

### Pitfall 2: `SetShellVarContext all` redirects `$APPDATA` and breaks the existing `..\..\ProgramData` walk

**What goes wrong:** Wrapping a large block (e.g., the entire install section) with `SetShellVarContext all`. The existing uninstaller code at lines 666-676 uses `"$APPDATA\..\..\ProgramData\..."` as a walk to `%ProgramData%` — that walk only works in the default `current` context.
**Why it happens:** `SetShellVarContext all` redirects `$APPDATA`, `$LOCALAPPDATA`, `$DESKTOP`, `$STARTMENU`, AND `$SMPROGRAMS` `[CITED: nsis.sourceforge.io/Reference/SetShellVarContext]`.
**How to avoid:** Tight wraps. Set `all` immediately before `CreateShortcut`/`Delete` for `$SMPROGRAMS` only, restore `current` immediately after. Better: stop using the `..\..\ProgramData` walk entirely and use `SetShellVarContext all` + `$APPDATA` (which then equals `%ProgramData%`) — but that's a Phase-11.1-out-of-scope refactor; keep the wraps tight in this phase.
**Warning signs:** Pester item 4 (`previous-mail-client.json` exists at `%ProgramData%\go-mapi\uninst\`) starts failing after a "minor" NSIS shortcut change.

### Pitfall 3: `schtasks /create` swallowing "task already exists" without `/F`

**What goes wrong:** Reinstall flow runs `schtasks /create /XML ...` without `/F`. First install succeeds; reinstall fails with rc=1 "The task already exists." Installer continues with detail-print noise but the task is now stale (still pointing at the previous `$INSTDIR` if the user picked a different one).
**Why it happens:** `schtasks` exit codes are non-discoverable; rc=1 looks like generic failure.
**How to avoid:** Always pass `/F` when creating from XML in an installer. `/F` suppresses the warning and overwrites the existing task `[VERIFIED: Microsoft Learn schtasks-create]`.
**Warning signs:** Reinstall on a machine with auto-update enabled doesn't propagate `$INSTDIR` change to the task action path.

### Pitfall 4: Bare `MoveFileEx` rename without `MOVEFILE_REPLACE_EXISTING`

**What goes wrong:** Calling `MoveFileEx(staged, installed, 0)` directly without first renaming the existing `installed` aside. NTFS rejects with `ERROR_ALREADY_EXISTS` (183) because the destination exists.
**Why it happens:** Reading `MoveFileEx` docs and seeing `MOVEFILE_REPLACE_EXISTING` as "the obvious flag" — but using it on a running EXE/DLL fails because Windows tries to delete the destination FIRST, and the destination is held with `DELETE` access only by the loader (which doesn't permit `OPEN_EXISTING; FILE_SHARE_DELETE` revocation by another caller).
**How to avoid:** Two-step pattern (Pattern 4 above): rename `installed → installed.old.<pid>` first (this works because the loader's handle holds `FILE_SHARE_DELETE`), THEN rename `staged → installed` with no flags.
**Warning signs:** First swap attempt during silent update fails with rc=183 or rc=32 (`ERROR_SHARING_VIOLATION`).

### Pitfall 5: Polling `Get-ScheduledTask` from Pester before the task is committed to disk

**What goes wrong:** Test runs `schtasks /create /XML ...` then immediately `Get-ScheduledTask -TaskName "go-mapi Auto Update"`. On a slow runner the task object isn't visible yet; assertion fails intermittently.
**Why it happens:** Task Scheduler service caches tasks asynchronously. `schtasks /create` returns when the XML file is written under `%SystemRoot%\System32\Tasks\` but `Get-ScheduledTask` reads via the COM API which polls the cache.
**How to avoid:** Add a `Start-Sleep -Seconds 1` between `schtasks /create` and the assertion, or retry the `Get-ScheduledTask` call up to 3x with 500ms backoff.
**Warning signs:** Pester item flakes on the runner — passes locally, fails ~10% of CI runs.

### Pitfall 6: Logging the SHA-256 hash of a downloaded binary considered telemetry by overzealous reviewers

**What goes wrong:** `update.log` includes lines like `verified asset hash 7a8f...` — feels like privacy-clean diagnostic but a strict reviewer reads it as content-fingerprinting telemetry.
**Why it happens:** CLAUDE.md privacy baseline forbids "long-term storage of message content" but is silent on hashing release artifacts.
**How to avoid:** Log only `verified asset OK` / `verified asset FAILED (got != expected)` — no hex digest in logs. The full digest goes to GitHub Actions logs at release time only.
**Warning signs:** N/A — this is preventative, log format set in plan.

### Pitfall 7: `--update-check-silent` accidentally booting the tray during init

**What goes wrong:** Flag is parsed AFTER `wails.Run` because main.go reads `os.Args` lazily. Wails initialises WebView2, fyne tray, the watcher — then we exit. SYSTEM context can't initialise WebView2 (no display session 0) → silent crash.
**Why it happens:** Adding the flag check inside `app.go` `OnStartup` is "the natural place" but too late.
**How to avoid:** Parse the flag at the very top of `main()`, BEFORE `acquireSingleInstance`, BEFORE `checkWebView2`, BEFORE `checkOAuthCredentials`. The silent path runs its own routine and exits with `os.Exit(0)`. Use the existing build-tag split pattern: silent path lives in a non-`bindings`-tagged file so `wailsbindings.exe` introspection skips it.
**Warning signs:** Task Scheduler History tab shows "Last Run Result: 0xC0000005" (access violation) — that's WebView2 failing under session 0.

- The "rebuild every machine to ship an update" model the silent path retires for admin-managed deploys.
- Hand-rolled HTTP + SHA-256 verify code that some autoupdate implementations carry — go-selfupdate's `ChecksumValidator` covers it. Don't write it.
- `MOVEFILE_DELAY_UNTIL_REBOOT` for in-place updates of long-lived processes — works on a desktop PC, breaks on never-rebooted RDS hosts.

## Open Questions

1. **Should the `--update-check-silent` path also re-acquire OAuth tokens or touch the keyring?**
   - What we know: D-15 says no Wails UI changes; the silent updater downloads + verifies + swaps and exits.
   - What's unclear: Some failure modes (e.g., 401 from the GitHub API on a corporate proxy) might benefit from logging proxy/network state — but that's diagnostic, not auth.
   - Recommendation: Silent path only does public GitHub Releases requests. NO keyring touch, NO OAuth flow. The silent updater is decoupled from the user's Gmail credentials.

2. **What's the cleanup policy for `update.log` rotation?**
   - What we know: Log lives at `%ProgramData%\go-mapi\updates\update.log`, append-only.
   - What's unclear: Over years of daily writes, the log will grow. Cap at 1 MB? Rotate to `update.log.1`? Just truncate at 1 MB?
   - Recommendation: Truncate-at-startup-if-over-1MB. Simple, no log-management library, admin can grep with one tail.

3. **Should the install-time UI checkbox default change between consumer and enterprise installs?**
   - What we know: D-07 default OFF, `/AUTOUPDATE=1` overrides.
   - What's unclear: Is there a way to detect "this is an enterprise/MDM context" and flip the default? `Get-CimInstance Win32_ComputerSystem PartOfDomain` would work but adds an `nsExec` PowerShell call to install path.
   - Recommendation: Keep default OFF universally for v3.0. Enterprise admins who want it ON pass `/AUTOUPDATE=1` in their MSI/SCCM/Intune wrapper script — that's a 5-character delta in their existing tooling. Revisit at v3.1 if friction reports surface.

4. **Should the silent updater verify the RUNNING `go-mapi.exe` against `SHA256SUMS.txt` before swap to detect "user manually replaced the binary with their own build"?**
   - What we know: Out of scope per D-11 (no Authenticode either).
   - Recommendation: Don't. Adds a hash-of-running-binary check that doesn't actually defend against anything (an attacker who can write `$INSTDIR` already controls what runs). The release-channel SHA-256 verify on the DOWNLOAD is the integrity gate.

## Security Domain

> `security_enforcement` is the project default. Phase 11.1 introduces a network-fetched + locally-applied binary swap path — security review is mandatory.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | The silent path uses unauthenticated GitHub Releases endpoints; SYSTEM context inherits no user identity. |
| V3 Session Management | no | No sessions. |
| V4 Access Control | yes | `%ProgramData%\go-mapi\updates\` ACL — Users read-only, prevents tampering with staged binaries. Inherited from `%ProgramData%` defaults; no extra control needed. |
| V5 Input Validation | yes | `SHA256SUMS.txt` parsing — validate format strictly (regex `^[a-f0-9]{64}\s{2}[A-Za-z0-9._-]+$` per line). Reject anything else. go-selfupdate's `ChecksumValidator` does this. |
| V6 Cryptography | yes | SHA-256 via `crypto/sha256` (stdlib) — never hand-roll. go-selfupdate uses `crypto/sha256`. |
| V12 File and Resources | yes | Atomic swap MUST be tamper-resistant: validate hash BEFORE moving staged file into `$INSTDIR`. Never swap a binary that didn't pass validation. |
| V14 Configuration | yes | Task definition XML: hardcoded `URI = \go-mapi Auto Update`, hardcoded `UserId = S-1-5-18` (SYSTEM SID, not a name — locale-independent). |

### Known Threat Patterns for {NSIS installer + SYSTEM-task auto-updater}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Attacker MITMs the GitHub Releases TLS endpoint and serves a malicious `go-mapi.exe` matching a forged `SHA256SUMS.txt` | Tampering | TLS pinning is overkill; relying on Windows root CA store + standard HTTPS validation. Threat reduces to "attacker has a valid CA cert for github.com" — an attacker who has that has bigger problems. Authenticode signing (deferred per D-11) closes this fully when SignPath gates 100% of releases. |
| Attacker writes to `%ProgramData%\go-mapi\updates\staging\` between download and swap | Tampering | SYSTEM + Administrators full, Users read-only — non-admin Users can't write staged files. Hash verify happens AFTER the file is closed and BEFORE the swap (verify-then-swap, not swap-then-verify). |
| Attacker installs a Scheduled Task with the same name `go-mapi Auto Update` pointing at a malicious binary | Spoofing | Task registration needs admin elevation (`schtasks /create /F /RU SYSTEM` requires elevation already). Pre-existing admin compromise is out of scope of any defense. |
| Attacker holds `go-mapi.exe` with `FILE_SHARE_READ\|FILE_SHARE_WRITE` (excluding `FILE_SHARE_DELETE`) to prevent legitimate updates | DoS | Retry loop per D-14 plus `MultipleInstancesPolicy=IgnoreNew`. Worst case: silent update is delayed; user can still install manually. Notify-only path (Phase 11) remains as floor. |
| Attacker triggers `--update-check-silent` repeatedly to download bandwidth | DoS | `MultipleInstancesPolicy=IgnoreNew` + 24h cadence in `updateService.MaybeCheck` (already in Phase 11). The flag invocation is local-only; no network attack surface. |
| Attacker abuses the `go-mapi-setup.exe /AUTOUPDATE=1` install path to register a SYSTEM task on a machine they have admin rights on | Elevation of Privilege | Already requires admin (UAC at install time). Same threat model as any other elevated installer. |
| Reading the response body from GitHub Releases without size cap | Denial of Service / OOM | Cap download at sane size (e.g., 50 MB — `go-mapi-setup.exe` is well under 20 MB per Phase 10 D-05). go-selfupdate's downloader uses standard `net/http` Get which streams to disk; explicit `io.Copy(dest, io.LimitReader(src, capN))` adds belt-and-braces. |

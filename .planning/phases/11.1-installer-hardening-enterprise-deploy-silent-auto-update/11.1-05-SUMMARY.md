# Phase 11.1 Plan 05: Scheduled Task + NSIS /AUTOUPDATE Wiring Summary

**Status:** Completed
**Phase:** 11.1
**Plan:** 05
**Subsystem:** Installer

## Substantive one-liner

Wired the OS-level Windows Scheduled Task that drives Plan 11.1-04's silent updater: NSIS installer parses `/AUTOUPDATE=N` (or honors a default-OFF UI checkbox), emits the Task Scheduler XML programmatically with `$INSTDIR` baked in, registers the SYSTEM-context `go-mapi Auto Update` task via `schtasks /create /XML /F /RU SYSTEM`, and the uninstaller idempotently removes the task + scrubs `%ProgramData%\go-mapi\updates` + sweeps `*.old.<pid>` orphans from the install dirs — with Pester regressions (items 22, 23, 24, 24b) covering D-18 cases 1, 2, 5, 6 and W7.

## Key Decisions

- **Custom nsDialogs page over FinishPage decoration.** Picked a dedicated `Page custom AutoUpdatePage AutoUpdatePageLeave` slotted between `MUI_PAGE_INSTFILES` and `MUI_PAGE_FINISH` rather than overloading the FinishPage with a `SHOWREADME`-style checkbox. Rationale: a security-relevant opt-in (creates a SYSTEM-context Scheduled Task) deserves its own header and body label, the page short-circuits cleanly on `/S` (silent install) and when `/AUTOUPDATE=1` was already set on the command line, and the binary `Abort`-pattern keeps NSIS UI flow simple.
- **Strict-bool `/AUTOUPDATE` parsing.** `${GetOptions} ... /AUTOUPDATE= $AutoUpdateFlag` returns the raw post-`=` string; downstream comparison is exclusively `StrCmp $AutoUpdateFlag "1"`. Anything else — `0`, `true`, empty, garbage — resolves to OFF. RESEARCH §T-11.1.05-03 injection-via-CLI mitigation: the parsed value never flows into `ExecWait` argument construction; only fixed `schtasks` command-line strings are ever concatenated.
- **FindFirst/FindNext loop for `un.ScrubOldOrphans`.** Chose the NSIS-canonical wildcard-scrub pattern over the simpler `Delete "*.old.*"` because NSIS `Delete` glob support for double-wildcard patterns is not explicitly documented to match `<base>.old.<pid>` filenames. The Pester item 24b regression is the ground-truth check that orphans are actually removed, regardless of which mechanism shipped.
- **Programmatic XML generation post-UAT (FIX #3).** The original e9b2693 implementation followed RESEARCH §Pattern 3 verbatim: stage `tasks/go-mapi-auto-update.xml`, then `nsExec::ExecToLog 'powershell.exe ... -replace ''INSTDIR_PLACEHOLDER'' ...'`. Sandbox UAT proved this pattern silently failed in production — the staged XML retained the literal `INSTDIR_PLACEHOLDER` because the nested-quote escaping in the nsExec command line prevented PowerShell from running the substitution at all. The fix replaces the entire stage-and-substitute chain with `FileOpen` + a sequence of `FileWriteUTF16LE` calls that emit the XML directly with `$INSTDIR` baked in. No PS, no quoting, no encoding indirection.
- **`FileWriteUTF16LE /BOM` (not `FileWrite`) for UTF-16 LE emission (FIX #4).** NSIS Unicode-build's plain `FileWrite` writes ANSI/UTF-8 single-byte chars — NOT UTF-16 LE — despite some older docs implying otherwise. Sandbox UAT caught this empirically: the staged file had a 0xFF 0xFE BOM followed by single-byte ASCII for `<?xml...`, which `schtasks /XML` decoded as garbage Chinese characters and rejected with `"sintaxis de documento no válida"`. The correct primitive is `FileWriteUTF16LE` (with `/BOM` on the first call only).
- **`/RL HIGHEST` removed from `schtasks /create /XML` (FIX #1).** schtasks rejects `/RL` when `/XML` is also passed (Spanish error: `"la opción /XML solo puede usarse con /S /U /P /RU /RP /F /IT /TN"`, rc=`-2147467259` / E_FAIL). The `<RunLevel>HighestAvailable</RunLevel>` element inside the XML carries the runlevel pin instead. `/RU SYSTEM` is kept — defensive override of `<UserId>S-1-5-18</UserId>` (typo guard).
- **`ReadEnvStr $0 PROGRAMDATA` replaces `$APPDATA\..\..\ProgramData` path math (FIX #2).** The existing comments in `go-mapi.nsi` (and `BackupPreviousMailClient`, `RestorePreviousMailClient`) claimed `$APPDATA\..\..\ProgramData` resolves to `C:\ProgramData` under default `current` shell-var context. Sandbox UAT B (planted `staging-marker.txt` survived in `C:\ProgramData\go-mapi\updates`) proved this wrong — the relative walk resolves to `<userprofile>\ProgramData`, a non-existent path. Switched to `ReadEnvStr` which is reliable across user and SYSTEM contexts. Other call sites in the file still use the broken pattern; out-of-scope per scope-discipline (Plan 11.1-01 commit `52af618` didn't touch them either, so they remain a deferred follow-up).
- **`tasks/go-mapi-auto-update.xml` kept as canonical reference.** Even though the file is no longer staged at install time after FIX #3, it stays in the repo as documentation-of-record for the task shape (principal, triggers, settings) — downstream maintainers reading the codebase find a clear human-readable spec without having to disassemble the FileWriteUTF16LE block.

## Deviations from Plan

### Auto-fixed Issues — caught by sandbox UAT, fixed in `52af618`

**1. [Rule 1 — Bug] `/RL HIGHEST` incompatible with `/XML` on `schtasks /create`**
- **Found during:** Sandbox UAT Test A (install with `/AUTOUPDATE=1` returned exit code 0 from the installer, but `Get-ScheduledTask` returned null; installer.log showed `schtasks /create rc=-2147467259`).
- **Issue:** `schtasks /create /XML <path> /TN <name> /F /RU SYSTEM /RL HIGHEST` rejects with `"la opción /XML solo puede usarse con /S /U /P /RU /RP /F /IT /TN"` (locale-dependent — Spanish on the sandbox). `/RL` and `/XML` are mutually exclusive.
- **Fix:** Removed `/RL HIGHEST` from the command line. RunLevel is pinned by `<RunLevel>HighestAvailable</RunLevel>` inside the XML body. `/RU SYSTEM` is kept as a defensive override of `<UserId>S-1-5-18</UserId>`.
- **Files modified:** `src/installer/go-mapi.nsi` (`RegisterScheduledTask`).
- **Commit:** `52af618`.

**2. [Rule 1 — Bug] `$APPDATA\..\..\ProgramData` resolves to a non-existent path under `current` shell-var context**
- **Found during:** Sandbox UAT Test B (planted `staging-marker.txt` at `C:\ProgramData\go-mapi\updates\`, ran uninstall, observed file survived → `updates_dir_after: true` before the fix).
- **Issue:** The existing comment in `go-mapi.nsi` claimed `$APPDATA\..\..\ProgramData` resolves to `%ProgramData%`. Empirically wrong: under default `current` shell-var context, `$APPDATA = C:\Users\<user>\AppData\Roaming`, so `..\..` walks to `C:\Users\<user>` and the resulting `C:\Users\<user>\ProgramData` is a non-existent directory. The `RMDir /r` against that path is a silent no-op.
- **Fix:** Replaced with `ReadEnvStr $0 PROGRAMDATA` + `RMDir /r "$0\go-mapi\updates"`. `ReadEnvStr` reads the `PROGRAMDATA` environment variable (set by the OS to `C:\ProgramData`) which is reliable across user/SYSTEM contexts.
- **Files modified:** `src/installer/go-mapi.nsi` (uninstall section, D-18 case 6 scrub).
- **Commit:** `52af618`.
- **Out-of-scope follow-up:** the same broken pattern is used elsewhere in the file (`BackupPreviousMailClient`, `un.RestorePreviousMailClient`, the existing `uninst\` removal). Not fixed in this commit per scope-discipline — those call sites pre-date Plan 11.1-05 and warrant a separate cleanup pass. Currently they "work by accident" because the relative walk lands inside the user profile; the writes go to `<userprofile>\ProgramData\go-mapi\…` which is harmless but useless. Plan 11.1-06 or a quick task should consolidate.

**3. [Rule 1 — Bug] `nsExec::ExecToLog 'powershell.exe ...'` substitution silently failed**
- **Found during:** Sandbox UAT inspection of `staged-xml-snapshot.xml` from a `/AUTOUPDATE=1` install — the file retained the literal string `INSTDIR_PLACEHOLDER` instead of `C:\Program Files\go-mapi`.
- **Issue:** The original Pattern-3 implementation staged `tasks/go-mapi-auto-update.xml` then ran `nsExec::ExecToLog 'powershell.exe -NoProfile -Command "$x = Get-Content … -replace ''INSTDIR_PLACEHOLDER'', [regex]::Escape(''$INSTDIR'') …"'`. Inside the nsExec single-quoted command line, the doubled `''` for embedded apostrophes in PowerShell interacts badly with NSIS string interpolation (`$INSTDIR`) and the resulting command line was malformed enough that PowerShell never ran the substitution at all (no error logged; the staged file was left as-is).
- **Fix:** Replaced the entire stage-and-substitute chain with programmatic XML generation: `FileOpen` + a sequence of `FileWriteUTF16LE` calls that emit the XML directly with `$INSTDIR` interpolated via NSIS-native string substitution. No PS, no quoting layer, no encoding indirection.
- **Files modified:** `src/installer/go-mapi.nsi` (`RegisterScheduledTask`).
- **Commit:** `52af618`.

**4. [Rule 1 — Bug] NSIS Unicode-build `FileWrite` writes single-byte chars, not UTF-16 LE**
- **Found during:** Sandbox UAT Test A initial run (with FIX #3 applied but using plain `FileWrite`). `schtasks /create /XML` rejected with `"sintaxis de documento no válida"`. Manual inspection of the staged file showed bytes `FF FE 3C 00 3F 00 78 00 6D 00…` — a UTF-16 LE BOM followed by ASCII single-byte chars for `<?xml`, which UTF-16 decoders read as `0x003C` (`<`), then garbage 16-bit code units that map to Chinese/Korean ranges.
- **Issue:** NSIS Unicode-build's `FileWrite` writes ANSI/UTF-8 single-byte chars to the file. The output cursor and BOM-emit-on-first-write behavior implies a UTF-16 LE file, but the actual chars are not encoded as UTF-16 LE. Some older NSIS docs still say `FileWrite` "writes Unicode strings" — this is misleading. The correct primitive for UTF-16 LE emission is `FileWriteUTF16LE` (with `/BOM` on the first call to emit the 0xFF 0xFE BOM).
- **Fix:** Replaced every `FileWrite` in `RegisterScheduledTask` with `FileWriteUTF16LE` (with `/BOM` on the first call only). Now the staged file is well-formed UTF-16 LE and `schtasks /XML` accepts it.
- **Files modified:** `src/installer/go-mapi.nsi` (`RegisterScheduledTask`).
- **Commit:** `52af618`.

**5. [Rule 1 — Bug] Pester item 22 enum assertions break under PS5.1**
- **Found during:** Sandbox UAT Test A — assertions `Should -Be 'Highest'` / `Should -Be 'IgnoreNew'` failed because `Get-ScheduledTask` under PS5.1 returns the raw int values (`1` for Highest, `2` for IgnoreNew). The harness recorded `principal_runlevel: 1` and `multiple_instances: 2` — both functionally correct but type-mismatched.
- **Issue:** PS5.1 and PS7+ resolve the enum values differently. PS7+ returns the friendly string; PS5.1 returns the underlying integer. Strict `Should -Be 'Highest'` rejects `1`. SYSTEM SID resolution is similarly split: PS5.1 returns the friendly name `SYSTEM`, PS7+ returns the SID `S-1-5-18`.
- **Fix:** Relaxed assertions to `Should -BeIn @('S-1-5-18','SYSTEM')` / `Should -BeIn @('Highest', 1)` / `Should -BeIn @('IgnoreNew', 2)`. Both forms accepted; portability across runners.
- **Files modified:** `src/installer/tests/installer.Tests.ps1` (item 22).
- **Commit:** `52af618`.

## Threat Model Notes

The threat register from `11.1-05-PLAN.md` was honored:
- **T-11.1.05-03 (Injection via /AUTOUPDATE=" malicious")** — strict `StrCmp $AutoUpdateFlag "1"` short-circuits anything other than the literal `"1"`; the parsed value never enters argument construction.

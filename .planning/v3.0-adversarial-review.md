## Cross-cutting

### Internal consistency

- Both files agree on the installer filename (`go-mapi-setup.exe`), license (LGPL-3.0-or-later), and Gmail/Google Workspace support. No factual contradictions found.
- README line 48 says go-mapi "checks for updates automatically and lets you know when one is ready" but the update mechanism is notify-only by default (user must re-run installer). ENTERPRISE.md line 73 clarifies this is opt-in via `/AUTOUPDATE=1`. The README implies update checking is always-on without being explicit that automatic *installation* is not — a gap that could confuse Bob.

### Footer cross-references

- README lines 65–68: correctly links to both `ENTERPRISE.md` and `DEVELOPMENT.md`. Links are relative and correct.
- ENTERPRISE.md: has no footer cross-reference back to README or DEVELOPMENT.md. An admin who jumps straight to ENTERPRISE.md has no in-document path to the main project page.

### Trust signals

- **Supported by specifics:**
  - "No telemetry" — ENTERPRISE.md lines 174–185 names every outbound network destination. Specific and verifiable.
  - "No content retention" — ENTERPRISE.md line 183 explicitly states "no message bodies, no recipient data" in the update log. Specific.
  - "SHA-256 checksums published with every release" — ENTERPRISE.md lines 137–141 gives the exact URL. Specific.
  - "DPAPI-scoped, per user" for credential storage — ENTERPRISE.md lines 187–189. Specific.

- **Unsupported (claim without specifics):**
  - README line 18: "email content never leaves the Gmail API" — no explanation of where it *does* go (the queue directory), what data the queue holds, or how long it persists. The claim is true but incomplete in a way that could backfire under scrutiny.
  - README line 6: "Completely open source" — no link to the source repository is given anywhere in the README. The license line links to `LICENSE` (the file) but not to the repo itself. Bob cannot click to "check the code."
  - ENTERPRISE.md line 8 (~40–50 MB RAM): no methodology cited, no measurement conditions stated.

### Known issues section read

- **Bob's reaction:** Worrying. A "Known issues" section in a v3.0.0 release README with an unquantified persistence bug reads as "not done yet." Bob's heuristic for software quality is "does it work or not." Vague qualifications ("some settings... may not persist") have no positive framing. This section as written is the single most likely reason Bob closes the tab.

## Net assessment

The README is lean and nearly right — the hook, install steps, and usage description are clean and appropriately non-technical. But three things undermine it: a vague Known Issues entry that signals instability at exactly the wrong moment, a missing screenshot, and the admin-prompt step which leaves a non-technical user unsure whether they're allowed to proceed. Fix those three and Bob installs. The ENTERPRISE.md is the stronger document — it covers the real admin concerns (registry footprint, silent install, firewall, uninstall residue, privacy posture) with genuine specificity, more so than most FOSS tools at this stage. Its weaknesses are tactical rather than structural: an ambiguous Authenticode signing status, a broken verification snippet, and a missing firewall rule definition will slow Carol down but not stop her. Both documents are close to GA-ready; the README's known-issues entry is the most urgent single fix because it actively damages trust for the target audience.
